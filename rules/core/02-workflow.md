# Operational Workflow Rules (행동 프로토콜 및 워크플로우 규칙)

에이전트가 시스템의 상태를 변경(파일 생성/수정, 쉘 명령어 실행)할 때 **[반드시]** 거쳐야 하는 절차적 강제 사항입니다.

---

## 🔄 1단계: 지시 해석 및 위험도 평가 (Directive vs. Inquiry)

사용자의 요청 성격을 먼저 분류하고, 작업의 규모를 판단하십시오.

- **명시적 지시 (Directive)**: "커밋해", "A파일 수정해", "테스트 실행해"와 같이 결과가 명확한 명령을 내린 경우 별도의 승인 단계 없이 즉시 `2단계: 실행`으로 진입합니다. (Low Risk 작업 포함)
- **탐색적 질문 (Inquiry) / High Risk 작업**: 명확한 명령이 없거나, 3개 이상 파일 수정 및 아키텍처 변경이 수반되는 경우 코드를 작성하기 전 **[반드시]** 설계 전략이나 분석 결과를 문서화/요약하여 사용자에게 **사전 승인**을 대기하십시오.

---

## 🔄 2단계: 실행 및 수술적 편집 (Execution & Surgical Edits)

- 필요한 파일만 정확하게 타겟팅하여 수정하십시오. (제공된 파일 치환/작성 도구 등 활용)
- 수술적 편집(Surgical Edit): 가급적 전체 파일을 덮어쓰기보다, 치환(Replace) 도구를 사용하여 변경이 필요한 특정 블록만 정밀하게 교체하십시오.
- 실행 전후로 불필요하게 전체 코드를 출력하는 행위를 지양하십시오.

---

## 🔄 3단계: 기계적 검증 (Mechanical Validation)

- 수정을 마친 후 임의로 성공을 선언하지 마십시오.
- **[반드시]** 터미널을 통해 프로젝트의 빌드, 린트, 테스트 명령어를 실행하여 변경 사항이 기존 시스템을 깨뜨리지 않았음을 기계적으로 증명하십시오.
- *참고: 프로젝트의 정확한 검증 명령어를 모른다면 사용자에게 실행 방법을 질문하십시오.*

---

## 🔄 4단계: 조건부 자가 치유 루프 (Conditional Self-healing)

3단계에서 에러가 발생한 경우, 에러의 성격에 따라 대응 방식을 분리합니다.

- **기계적 에러 (Linter/Formatter/Type 오류)**: AI가 에러 로그를 분석하여 스스로 코드를 수정하고 다시 3단계를 수행하십시오.
- **논리적 에러 (테스트 실패/스크립트 런타임 에러)**: 즉시 코드를 무한 수정하여 재실행하지 마십시오. 에러 로그의 핵심 원인을 분석하여 사용자에게 먼저 보고하고, `원인 분석 -> 해결 방안 제안 -> 사용자 승인 대기` 절차를 준수하십시오.
- **🚨 Fail-safe**: 기계적 에러라도 동일한 에러가 **3번 이상** 반복된다면 즉시 작업을 중단하고 사용자에게 개입을 요청하십시오.

---

## 🔄 5단계: 구현 완료 후 교차 검증 (Post-Implementation Cross-Validation)

- **독립적 감사 서브에이전트 기동**: 아키텍처 수준의 대규모 변경이나 복잡한 구현 작업이 완결되면, 메인 에이전트는 작업을 즉시 종료하지 않고 독립된 감사 서브에이전트(`auditor` 또는 `self` 서브에이전트)를 동적으로 정의(`define_subagent`) 및 호출(`invoke_subagent`)하여 코드 감사를 진행할 수 있습니다.
- **감사 피드백 반영**: 서브에이전트로부터 전달받은 코드 품질, 예외 케이스 처리, 또는 요구사항 미반영 사항에 대한 비판적 리포트를 검토하고, 필요한 조치를 취한 뒤 최종 하네스 검증을 통과한 후 사용자에게 결과를 보고하십시오.
